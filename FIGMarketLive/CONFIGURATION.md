# Configuration

The Configuration button and tray menu open the same dialog. Opening or browsing configuration leaves price sync and studies running. Confirmed dataset changes stop workers before writing; changed local database/adapter settings stop workers when configuration closes. Restart explicitly after these changes. Local settings retain plugin path and polling preferences; monitor definitions live in SQL.

## Database

Enter or update the SQL Server connection string, including Database / Initial Catalog. **Test database and schema** opens the target database, checks visibility of its required columns, SELECT permissions, price types, binary StudyHistory.Studies storage and dataset/price/study composite unique indexes. Failure to open the target triggers a best-effort master catalogue check to distinguish inaccessible from missing/not-visible databases. Lack of visibility is never reported as proof that the database does not exist.

Results list schema problems. Configuration creates additive provider, checkpoint and price-event schema when missing and migrates legacy provider settings as described below; it does not create databases or migrate text study outputs. Other tables and interval seed rows must already be present. The database test checks Service Broker, SUBSCRIBE QUERY NOTIFICATIONS permission, the MarketLive price-event trigger and actual notification delivery for the configured user. It commits a uniquely named test event and removes it afterward, without modifying prices or studies. If Broker is disabled, setup releases its own idle pooled sessions and attempts ENABLE_BROKER from master with a five-second lock timeout. Active operations are not aborted. Insufficient permission or database sessions preventing enablement fail the test with instructions; setup does not force-disconnect active sessions or grant privileges automatically.

**Configure SQL notifications…** is an explicit administrator action beside the database test. It shows the target database, application login and actual mapped database user. Use the configured connection if it has database CONTROL permission, or select SQL administrator username/password. Credentials are masked, used only for this operation, cleared on completion/cancellation and never saved to marketlive.json or logged.

After confirmation, local workers stop. If Broker is disabled, setup executes SINGLE_USER WITH ROLLBACK IMMEDIATE, ENABLE_BROKER and MULTI_USER from master. This forcibly disconnects database sessions and rolls back their uncommitted transactions. SQL CATCH and an independent recovery connection attempt to restore MULTI_USER even on failure/timeout. Recovery failure explicitly reports the restoration command. Already restricted databases and system databases are rejected before disruption. When Broker is already enabled, no SINGLE_USER transition is made.

Permissions are granted to the application database user resolved through USER_NAME(), which may differ from the connection string's User ID; integrated authentication is supported for the configured connection. A dbo mapping already has permissions and is not granted to. Other users receive SUBSCRIBE QUERY NOTIFICATIONS, CREATE QUEUE, CREATE SERVICE and REFERENCES on the query-notification contract. Database and user identifiers are quoted. The administrator account is never substituted as the application user. The normal database test reruns with the original application connection after setup to verify notification delivery.

**Backup study reconciliation poll (seconds)** appears below Maximum price catch-up. It saves `PollSeconds` to marketlive.json, defaults to 60 for new configurations and accepts 1–86,400 seconds. Existing configured values are preserved. Normal study updates use FIGCommon EventMonitorService in SqlDependency mode. The slower poll checks all enabled studies at startup and periodically, covering notification outages and missed events. Restart studies after saving changes to this interval. This setting does not control broker price-request pacing.

`dbo.trigMarketLivePriceDataChange` writes `MARKETLIVE_PRICEDATA` events keyed by DataSetId in the same transaction as PriceData inserts, OHLCV updates and deletes. It handles multi-dataset batches and suppresses unchanged-value updates. Events contain a revision token, so multiple changes sharing a timestamp are distinguishable. Existing application triggers are retained. The sync worker and importer write through this trigger; direct external bulk loaders must fire triggers or rely on backup reconciliation. Do not disable triggers for normal ingestion. The event rows are coalesced per dataset rather than appended per bar.

Notifications wake only studies using the affected source dataset, including aggregate studies. Repeated events coalesce; events arriving during calculation remain queued. The worker rereads authoritative SQL prices and retains checkpoint/source validation and atomic output publication. A full periodic reconciliation is not postponed by a stream of notifications. The existing EventMonitorService two-minute event scan is unchanged; backup reconciliation covers longer outages. Subscription session SET options are explicit, and shutdown callbacks use a safely cached cancellation token.

## Market-data adapter

Select the provider. The installed provider is **IBKR — TWS / IB Gateway**, hosted directly inside FIGMarketLive using IBKRProvider.dll. FIGBrokerSvc, its HTTP lookup endpoints and FIG authentication are not used by this workflow.

The dialog generates fields from the adapter's descriptor:

- Host: defaults to 127.0.0.1.
- API socket port: starting value 7497; match the port configured in your TWS/Gateway instance.
- Dedicated API client ID: starting value 31; use a positive ID not in use by another application on the same instance.
- API handshake timeout: starting value 15 seconds, after the SDK socket connection call returns.
- Request timeout: starting value 30 seconds for provider requests.

Log in to TWS or IB Gateway separately and enable its socket API access. FIGMarketLive does not accept your brokerage login password. **Connect / test** constructs the adapter, connects the socket and waits for the provider connection acknowledgment. It does not certify market-data entitlements: actual data requests can still fail. **Disconnect** drains active work before releasing the provider.

Changing settings invalidates cached test results but leaves ticker actions available. Search and dataset actions validate the current database and connect/reconnect the adapter on demand, without requiring manual test-button confirmations. Failures identify the Database or Market Data Adapter tab and the relevant test button. Closing or saving the dialog disconnects its configuration session. This session is for lookup/setup; continuous SQL price acquisition is not wired into the study worker yet. TWS socket establishment can take longer than the handshake timeout because the underlying synchronous SDK connect has its own socket behavior. Cancellation waits for active SDK work to drain rather than allowing overlapping calls or disposal while that work is running.

The Connect / test button has a result icon beside it: succes.png after a successful connection, fail.png on validation/connection failure. Retesting, changing adapter settings or disconnecting clears the previous result. Errors include the configured endpoint/client ID and the underlying SDK socket/error message when available. A refused connection means the endpoint did not accept the socket at that time; check that the adapter port matches the running TWS/Gateway instance rather than assuming the starting port is correct.

Stock search uses provider SymbolLookup; selection is resolved through ContractInfo before saving to SQL. Futures search uses ContractInfo for an explicit YYYYMM contract month or YYYYMMDD expiry. The current provider interface returns one resolved futures contract, not a chain of all expiries. Include exchange and currency to disambiguate.

Existing configuration files remain readable. The retired Broker URL/account/token section is ignored and removed when saving. Existing monitor definitions are preserved. Legacy broker-backed dataset selections should be reselected through the direct adapter so provider-neutral instrument metadata and provider identity are recorded. Connection strings remain local JSON; prefer integrated authentication.

## Provider-neutral extension contract

`FIGMarketLive.Core/MarketData/IMarketDataAdapter.cs` defines connection/disconnection, instrument search/resolution, historical OHLCV and last-price snapshots. Its public contracts contain no IBKR SDK types, HTTP credentials or trading operations. Provider instrument IDs are strings; bar volume and multipliers retain decimal precision at this boundary. Existing SQL/model limits are checked separately when saving.

`IMarketDataAdapterFactory` supplies the descriptor, parameter defaults, validation and instance construction. `MarketDataAdapterCatalog` selects factories by ProviderId. A future adapter implements these interfaces and is registered in the application composition root; the database, study code and configuration form do not need provider-specific branches. Field generation and help text come from the selected descriptor. Dynamic loading of adapter assemblies is not implemented.

The IBKR implementation lives in FIGMarketLive.Adapters.IBKR. It owns SDK mapping, callback/connection infrastructure and serialized background execution. Snapshot results are prices, not complete OHLCV bars; use GetHistoricalBarsAsync for authoritative bars. Requests are serialized, but a provider-specific historical pacing scheduler remains future work. No trading or position-tracking services are started.

## Ticker and DataSet

The third tab always offers search and dataset setup; actions are temporarily disabled only while an operation is running. Compact search fields accept the symbol, FUT/STK type, exchange, currency and expiry. Select an instrument and an interval loaded from dbo.Interval, then use **Save Ticker** beside Interval to create/reuse its ticker and dataset. The Market Data Adapter tab uses Branding/plug.png.

**Local database symbol** is the local unique key. Futures default to the resolved local contract symbol so different expiries can coexist under the existing unique Ticker.Symbol constraint. Shared contract metadata remains in Ticker; provider symbol and instrument ID are saved in TickerProvider. Provider IDs are never reused as local Ticker or DataSet identity values.

**Save Ticker** re-resolves the selected contract, verifies its ID when available, validates its minimum tick and integer multiplier, then transactionally inserts/reuses Ticker, DataSet and TickerProvider. A conflicting local symbol is rejected; existing shared contract metadata is not overwritten. Database writes happen when this button is clicked, even if the dialog is subsequently closed without saving configuration. **Save configuration** saves connection/adapter/application settings, not dataset selections. Draft settings can be saved without passing tests; search and SQL setup validate connections on demand.

Configured price datasets appear in a multi-column grid with dataset ID, symbol, contract, security type, interval, StudyCol count and enabled SQL monitor count. Configuration loads this list from SQL when opened, and refreshes it after successful database checks and ticker saves. There is no JSON dataset fallback. If SQL cannot be accessed, the database test reports the problem and the list remains empty. There is no separate Load existing DataSets button or dataset dropdown.

### Delete a dataset

Select a row and use **Delete selected DataSet**. The application previews the actual SQL dataset and every StudyCol with its ticker/interval (StudyCol has no DataSetId in this schema). Confirmation identifies the dataset, price/study row counts, and warns that all dependent StudyCols and configured monitors will be removed. No is the default response.

The first SQL refresh preserves selection by DataSetId, even if row order or display labels change. Before confirmation, the selected dataset is validated by DataSetId, TickerId and IntervalId rather than broker/root symbol text. Confirmation uses the current SQL names. If the selected dataset disappears, selection is cleared instead of moving the delete action to another row.

After confirmation, a serializable transaction rereads and locks the dataset and StudyCol dependencies. Changed identity, StudyCol IDs or ticker ownership cancel deletion and require a fresh confirmation. It deletes dependent StudyHistory output/checkpoint rows, matching StudyCol rows, PriceData and the DataSet row. If no other datasets use the ticker, confirmation includes removal of its remaining study definitions, TickerProvider mappings and Ticker row. Shared tickers remain. Unrecognized cascading relationships are rejected; other foreign-key failures roll back the entire transaction.

Removing dependent SQL StudyCol rows also removes their runtime monitors; there are no local monitor definitions to clean up. Closing the dialog does not undo deletion. If the database connection was edited, save/reopen configuration before deletion so identities cannot refer to a different configured database.

## TickerProvider and legacy settings migration

TickerProvider has a primary key on (TickerId, ProviderType), a foreign key to Ticker, a string ProviderInstrumentId (IBKR ConId or another provider's ID), and ProviderSymbol (for example NQ while the local ticker is NQZ6). Exchange, currency, expiry, minimum tick and multiplier remain in Ticker. DataSet retains ticker/interval associations. The SQL-backed reader reconstructs a provider-neutral instrument from these tables.

On database testing/opening Configuration, the app creates TickerProvider if absent. When legacy DataSelections exists, it validates each entry against its SQL dataset identity, deduplicates provider metadata by ticker/provider, and commits all mappings together. Conflicting metadata, unknown providers or missing parent identities stop migration without removing JSON. Existing mappings may be enriched with previously unknown IDs but are not silently replaced during migration.

Only after SQL commit does the app remove DataSelections from the active settings file. A `marketlive.json.before-ticker-provider-*.bak` backup retains the original. The app checks for concurrent file changes and keeps legacy JSON on migration/save failure so rerunning is safe. Do not commit settings backups; they may contain the same connection credentials as the original. New settings files omit DataSelections completely. Saving a different database connection is blocked until nonempty legacy entries have migrated to their original database.

For explicit migration without opening Configuration:

```powershell
dotnet FIGMarketLive/bin/Release/net10.0-windows/FIGMarketLive.dll --migrate-provider-settings PATH_TO_MARKETLIVE_JSON
```

Creating the new table requires suitable SQL schema permissions. Database/CreateTickerProvider.sql is available for manual installation. No existing Ticker/DataSet rows or price/study data are deleted by migration.

Every enabled SQL StudyCol becomes a runtime monitor. Dataset selection is automatic using the same compatibility rules as the editor. Broker price acquisition remains a later integration step.

## Live Studies

This tab uses bar-chart.png and edits dbo.StudyCol directly. On first opening it loads the current SQL catalog. The toolbar above the configured StudyCol table provides Add (add.png), Delete (trash.png), Save (save.png), a separator, and Refresh (reload.png). Tooltips describe each action. Refresh reloads SQL definitions and later ColType changes; Add clears the editor and shows New StudyCol. Selecting a row loads its values beneath the table with Editing StudyCol <id>. Switching tabs preserves the current editor draft.

- Ticker contains only SQL tickers with at least one configured DataSet.
- Interval contains direct datasets and intervals that can be aggregated without splitting source bars. A five-minute dataset supports ten/fifteen/twenty/thirty minutes, hours divisible by five minutes, and calendar days. A larger source cannot create smaller bars or incompatible multiples.
- An exact target dataset is preferred; otherwise the closest compatible source is chosen deterministically. The editor shows that source dataset and whether aggregation is required. Month/week/year compatibility is evaluated as calendar units rather than the schema's approximate number of seconds per month/year.
- ColType comes from dbo.ColType. ColParams is a multiline JSON object editor with a format/validate action; malformed or case-ambiguous duplicate parameters are rejected.
- Enabled is an editable checkbox. Study Collections displays OrderSeq and has Move Up / Move Down toolbar actions (up-arrow.png / dn-arrow.png). Moving a selected row immediately saves a contiguous sequence across all collections, including disabled ones, in one SQL transaction. Stale order snapshots are rejected and require Reload. New studies append; editing preserves order. Live execution and selected-type regeneration process OrderSeq ascending, then StudyCol ID to resolve legacy ties. Order-only edits do not invalidate calculated outputs/checkpoints. An active run retains its current ordering until the next pass; restart studies to apply immediately.

The toolbar **Save** validates dataset compatibility and ColType again inside its SQL transaction. Save is enabled only when required selections are present and draft values differ from the loaded/new baseline. It writes immediately; local Save configuration is separate. The running worker reloads enabled studies and their source datasets each polling pass, with runtime UTC aggregation for compatible intervals. Existing DLLs still use the FIGSignalSvc plugin package/manifest loader, and the manifest is authoritative for DLL selection; SQL DLLName is a synchronized mirror. Historical outputs are not automatically deleted if a new configuration changes the output timeline.

## SQL-driven runtime monitors

Monitors is no longer an active JSON setting. Startup/configuration validates legacy StudyCol references and SQL source compatibility, backs up the file as `marketlive.json.before-sql-monitors-*.bak`, then removes the old section. Missing/incompatible definitions retain the legacy JSON for correction. The normal runtime uses all enabled SQL studies, independent of legacy settings; disabled/deleted studies stop on the next pass. Changes to source choice, target interval, ticker metadata, DLL assignment or JSON parameters invalidate the study cache and cause a fresh replay. Other valid monitors continue if one definition is invalid. No enabled studies produces an attention message while the worker waits for configuration.

Exact interval datasets are preferred. Otherwise the closest/largest compatible source is selected, with the lowest dataset ID breaking ties. Only existing source prices are aggregated: OHLC is first/max/min/last and volume is summed with overflow checking. Partial first/current target bars are retained. No artificial bars are inserted across gaps. Source bars must fit wholly within target boundaries.

Aggregation is explicitly UTC-based, not exchange-session based: intraday periods are anchored at Unix epoch, daily periods at UTC midnight, weeks on Monday, and months/years on real calendar boundaries. Multi-period day/week/month/year groups use consistent epoch-based anchors. A futures exchange trading day can differ from a UTC day; session/timezone aggregation remains future work. Aggregates are calculation inputs and StudyHistory output rows; they do not create duplicate PriceData datasets.

Publication rereads raw source prices and SQL configuration under the transaction before accepting results. It validates output coverage against the aggregated timeline rather than comparing target bars to every raw source bar. Compatible checkpoints allow replay of only the affected suffix; source corrections invalidate checkpoints whose input prefix has changed.

### Study checkpoints

`CheckpointsEnabled` defaults to true and `CheckpointEveryBars` defaults to 5,000 in marketlive.json and is editable in Configuration → Database (Checkpoint interval). Save and restart the study worker to apply it. StudyHistory schema setup is additive and runs during database testing and study startup. The same native checkpoint serializer as FIGSignalSvc is linked into MarketLive. Collection DLLs must support native checkpoints; unsupported collections continue with full replay and report that status.

The first calculation establishes checkpoints. Scheduled snapshots and the newest completed bar are saved once the cadence is reached; the final forming bar is always replayed. Restart validates the definition, DLL identity, source inputs and existing published prefix before restoring. Earlier corrections select an earlier compatible checkpoint. Missing, malformed or incompatible state falls back to replay. Both legacy embedded-price snapshots and bounded price-window snapshots are supported.

StudyHistory is the single output table: Studies is varbinary(max) in FIGS format, alongside per-bar OHLCV, native JSON CheckpointState, save time and input-prefix metadata. BarStudy is obsolete. Outputs, checkpoints and progress commit together, and unchanged values are not rewritten. Checkpoint payloads and prefix metadata are bulk-staged and updated together, with no per-checkpoint metadata commands. Study batch size and checkpoint interval are independent: a 15,000-bar batch with a 5,000-bar checkpoint interval normally stores three checkpoints in one transaction. Batch boundaries also capture recovery state; the final forming bar is excluded from checkpoints. Every captured snapshot is persisted, never evicted. If accumulated serialized checkpoints reach 64 MiB, the current batch commits early; a single snapshot is limited to 64 MiB, so buffered serialized payloads remain below 128 MiB. Normal configured batch boundaries remain fixed after an early memory flush. The final remainder can be smaller than the configured batch size. Start Studies rereads the configuration and displays both values. The worker still reads and hashes source history for validation, so checkpointing reduces calculation work rather than eliminating historical SQL reads. Configure one writer per StudyCol.

Database testing and study startup migrate old storage transactionally, preserving valid binary outputs and checkpoints, converting supported scalar JSON values through the FIGS codec and removing BarStudy after verification. Unknown nested JSON/dependencies abort migration without deleting original data. Empty legacy placeholders are not treated as calculated outputs; checkpoints past missing output coverage are invalidated. An explicitly authorized --reset-study-storage operation truncates StudyHistory, clears regeneration progress, changes Studies to binary and drops BarStudy while retaining PriceData and definitions. This reset was applied to the configured FIGMarketLive database on November 1, 2026; its two StudyCol definitions remained with zero history rows immediately afterward.

Every write batch records elapsed milliseconds for connection/setup, metadata/source validation, bulk staging, StudyHistory output upsert, checkpoint cleanup/staging/upsert, progress and commit. Full detail is logged in `%LOCALAPPDATA%\FIGMarketLive\marketlive.log`; progress messages show total database time and the slowest stage. Failed/uncommitted writes are labelled accordingly. Forward regeneration invalidates future checkpoints once at the first resumed batch; subsequent batches prune only the previous temporary boundary checkpoint by indexed timestamp. Per-batch timings include server waits and client/network overhead, not CPU study calculation time. Earlier isolated tests of the previous multi-checkpoint batching implementation measured approximately 160–206 ms for 1,000 bars; those timings are not a production throughput estimate or a benchmark of the current batching.

Explicit legacy cleanup:

```powershell
dotnet FIGMarketLive/bin/Release/net10.0-windows/FIGMarketLive.dll --migrate-sql-monitors PATH_TO_MARKETLIVE_JSON
```

## Collection Types

Collection Types is a read-only plugin inventory with a Refresh action. It displays collection type, manifest-selected DLL, factory version, plugin/manifest path, load status and errors. Selecting an entry shows full error details. It uses the same managed package loader as FIGSignalSvc, including API/factory validation. Malformed manifests, missing DLLs, dependency failures, missing folders and duplicate types are shown. Ambiguous duplicate types cannot run.

The Plugin folder field has Browse and Save plugin folder controls. For example, select `C:\Roots\Backtesting\Plugins`; each package beneath it needs plugin.json, its declared DLL and dependencies. The path is stored as PluginPath in marketlive.json. Relative paths resolve against that configuration file. Unsaved path changes prompt Save / Cancel on tab navigation or closing. Refresh uses the saved folder. New/changed packages require restarting studies; the discovery cache refreshes when manifest/DLL files change.

Successfully loaded manifests automatically insert missing dbo.ColType rows and update their mirrored DLLName values at study startup, database testing, plugin refresh and Live Studies reload. Existing descriptions are preserved. SQL DLLName no longer selects or validates the runtime DLL: the manifest and loaded factory are authoritative. Missing/broken plugins leave existing SQL types and StudyCol references intact and display as unavailable. Live Studies offers only successfully loaded types for new assignments. Install/fix the package and refresh instead of manually adding SQL types.

Dataset dependency previews and deletion now use the same interval/source-selection rules, including studies aggregated from the selected source dataset. The dependency list is still rechecked after confirmation inside the deletion transaction.

## Branding and tray status

The executable and both windows use Branding/FIGMonitor.ico. PNG/ICO assets are embedded in the assembly, so source-folder paths are not required at runtime. Configuration, Start studies and Pause buttons (and their tray menu entries) use settings.png, play.png and pause.png. The Database and Ticker/DataSet tab headings use database.png and chart.png.

The tray uses FIGMonitorOff.png while idle, paused or connecting; FIGMonitorOn.png only while monitoring is active and its runtime adapter is connected; FIGMonitorWarning.png takes priority for study/database errors, deferred publication or a lost adapter connection. Warnings are retained per StudyCol and cleared when that collection succeeds; another collection's success does not clear them. Pause resets study attention; stopping price sync resets price attention. The tray tooltip also describes the state.

Start studies runs the SQL study worker independently of the broker. Start Price Sync owns the runtime adapter connection. ## Price sync

The main window defaults to **Start Price Sync**, with stock-sync.png tinted red. After the adapter connects, the button becomes **Stop Price Sync** and the icon turns green. Stopping cancels retrieval, awaits pending adapter work and disconnects. Lost connectivity turns the icon red while retaining Stop Price Sync so the worker can be stopped. Live Studies and price sync run independently; Pause affects studies only. The tray turns on for connected price sync; warnings take priority.

Price sync reloads SQL datasets with DataSet.Monitor enabled each pass and uses TickerProvider mappings for the selected adapter. Intraday intervals supported by the adapter are requested as authoritative OHLCV bars, including recent bars for corrections and the forming bar. A serializable transaction checks the dataset identity and inserts missing or updates changed PriceData rows. Unsupported intervals, missing mappings, invalid OHLCV or volume exceeding SQL int capacity produce per-dataset warnings. Calendar source capture is not implemented; calendar Live Studies can aggregate intraday datasets.

PriceHistoryMinutes in marketlive.json defaults to 7,200 minutes / five days (range 1–43,200 minutes / 30 days). Retrieval is bounded to that history window. Empty/stale datasets generate an import/coverage warning, retained for the session; restart sync after importing missing history. This does not prove continuity across market sessions. No synthetic bars are added and old prices are never deleted. Multi-day history is split into daily requests (one-hour requests for bars below one minute). Requests run sequentially with at least 11 seconds between request starts and a minimum five-second pass delay to reduce pacing pressure. PollSeconds controls backup study reconciliation independently. Provider-specific pacing across other applications remains outside this worker.

Live broker retrieval and SQL price publication must still be verified against the configured broker/database; automated checks do not connect to them.
## Tools — Import e-Signal Prices

The main-window Tools button after Configuration uses tools.png and opens its own FIGMarketLive Tools dialog. The first tab is Import e-Signal Prices with import.png. Tools is separate from Configuration and is also available from the tray menu. Opening Tools, analyzing datasets and previewing imports leave workers running. Confirming an import stops price sync and Live Studies before writing prices. Stop messages include the reason. Additional tools can be added as tabs later.

Tickers load immediately when Tools opens (all SQL tickers, including ones without datasets). Refresh Tickers reloads the list, preserving the selected ticker when available. Choose a CSV/text file, select the ticker and source timezone, and preview. The source timezone defaults to local; conversion uses timezone daylight-saving rules and rejects ambiguous/nonexistent timestamps. The shared FIGPriceCsvConverter reader recognizes Date, Time, Open, High, Low, Close with optional Vol/Volume and ignores other export fields such as Bar#, Bar Index and Tick Range. Missing volume produces a visible warning and writes zero for imported rows, including updates. The standalone converter still requires volume.

Rows are sorted chronologically, independent of export order. Interval inference takes the smallest positive timestamp spacing and checks that all gaps are multiples. Verify the detected interval in the preview: sparse exports can look like a larger interval. At least two bars are required. Duplicate timestamps, malformed prices, mixed spacing, volume overflow and non-e-Signal headers are rejected. The interval must already exist in dbo.Interval; the tool does not create interval definitions.

The preview shows SQL/file ranges, counts and the exact planned operation. An absent ticker/interval DataSet requires explicit approval to create it; declining performs no writes. If the file starts before existing prices, the confirmed import deletes all PriceData for that dataset and imports the complete file, even if that shortens the end of the existing range. Otherwise, a file ending after existing prices updates matching timestamps and inserts missing file bars, preserving prices outside the file. Files wholly contained in existing coverage (including identical ranges) are reported as no change. First/last always mean chronological oldest/newest.

Import uses staging/bulk copy and a serializable transaction. SQL metadata and an SHA-256 fingerprint of existing dataset prices are checked again after confirmation; concurrent changes force a new preview. Failure/cancellation rolls back dataset creation and price changes. StudyHistory is retained; restart Live Studies to recalculate. If replacement removes timestamps already represented in StudyHistory, the study worker may require a deliberate history rebuild rather than silently deleting study output. No real price imports were executed during development verification.

The maximum price catch-up control is on Configuration → Database and saves PriceHistoryMinutes. The default is 7200 (five days).
## Dataset price-sync flag and exchange schedule

Configuration → Ticker and DataSet lists StudyCols as In Use / NOT Used and Monitor as Enabled / Disabled. Study usage includes exact and aggregate-source dependencies, including disabled StudyCols. Enable / disable price sync for selected DataSet saves dbo.DataSet.Monitor immediately. This flag is independent of StudyCol.Enabled. Existing and newly created datasets default to Monitor=0; enable only the datasets that should capture broker prices. Start Price Sync also needs to be running.

Configuration → Exchange Schedule (sync_sched.png) edits dbo.ExchangePriceSchedule. Select a row or New schedule, set exchange name, enabled status, timezone, weekly break start/end weekdays and times, and daily break start/end times. Save commits immediately. Times use HH:mm in the exchange timezone, with daylight-saving conversion handled by the same FIGCommon MarketScheduleHelper used by FIGPriceSyncSvc. Break starts are inclusive and ends exclusive. Midnight-crossing closures are supported. Equal break endpoints are rejected. These are repeating weekly/daily rules, with no holiday calendar or product-specific exceptions.

CME is initially seeded from FIGPriceSyncSvc/price-sync-settings.json: Central Standard Time; weekly closure Friday 16:00 through Sunday 17:00; daily break 16:00–17:00. Other existing ticker exchanges get disabled placeholders that must be configured before use. Existing schedules are not overwritten by schema setup. Exchange matching uses Ticker.Exchange, not the provider name or symbol.

Every explicit **Start Price Sync** performs one catch-up pass for the datasets currently marked Monitor, even outside schedule hours or when the schedule is disabled. It refreshes from the last stored bar within PriceHistoryMinutes, using normal validation, pacing, rollover boundaries and transactional writes. A missing/invalid schedule is still a configuration error. A failed startup request is reported; outside schedule hours it is not repeatedly retried. Stop and Start explicitly requests another catch-up.

After this initial pass, disabled/closed schedules prevent automatic capture. The worker checks before every scheduled history request, during publication and immediately before committing; closure discards that scheduled batch for retry on reopening. The main window has a dedicated status area listing each exchange as running or **Waiting for exchange schedule**, with its next scheduled start in exchange-local time, UTC offset and timezone. Disabled schedules have no automatic next start. Polling detects edited schedules and openings without restarting. Manual historical e-Signal import is independent of the live schedule.

## RawTime-only PriceData migration

PriceData stores RawTime as its sole timestamp; PriceDate is removed. The managed PriceDataRS.PriceDate property remains available to existing collection DLLs, calculated from RawTime when loading SQL rows. Import, capture, snapshot hashing and shared repository loading no longer require a stored date. Shared bulk import also supports older databases that still have the stored column.

The idempotent migration adds DataSet.Monitor bit NOT NULL DEFAULT(0), removes PriceDate, and creates/seeds exchange schedules:

```powershell
dotnet FIGMarketLive/bin/Release/net10.0-windows/FIGMarketLive.dll --migrate-price-schema PATH_TO_MARKETLIVE_JSON
```

The migration refuses to drop PriceDate if legacy SQL modules reference it. --audit-price-schema JSON_PATH OUTPUT_SQL_FILE reports those dependencies. Configuration schema checks report any remaining stored PriceDate. Restart/rebuild the app after migration so an old executable does not use the removed column.
## Editing a continuous ticker contract

In Ticker and DataSet, select an existing dataset and click Edit selected ticker contract / expiry. The editor displays the stable database symbol and provider root, and allows the contract LocalSymbol and futures expiry (YYYYMM or YYYYMMDD) to change. Resolve and save contract queries the active market-data adapter without the old provider instrument ID, validates the requested contract, then updates the existing Ticker and TickerProvider atomically. The resolved contract must retain root, type, exchange, currency, minimum tick and multiplier. Stocks have no editable expiry.

This updates the ticker for ALL its datasets. Ticker ID, database Symbol (such as NQ#F), dataset IDs, Monitor flags, StudyCols, PriceData and StudyHistory are preserved. No new ticker or dataset is inserted. The configured dataset grid also displays expiry. SQL metadata is checked again when saving so concurrent edits force reopening the editor.

An actual contract roll records TickerProvider.HistoryStartRawTime at save time. Automatic capture only publishes new-contract bars whose opening timestamps are at/after that boundary; this protects earlier continuous history from the overlapping catch-up request. The first new-contract bar can arrive at the next interval opening. This is an explicit immediate roll, without back-adjustment or historical reconstruction. Correcting a local label or normalizing month expiry to an exact date for the same provider contract preserves its existing capture boundary. Other provider mappings have stale contract IDs cleared on a roll. Price publication also rechecks provider metadata transactionally, discarding retrieval made against an outdated contract.

The nullable history boundary column is added idempotently by normal provider schema setup. No existing ticker is rolled just by upgrading the application.

## Tools: Regenerate Studies and large-history batches

Tools → **Regenerate Studies** (regenerate.png) lists SQL collection types, configured StudyCol counts, enabled counts and plugin availability. Select multiple rows with Ctrl/Shift, then **Regenerate selected collections**. Only enabled StudyCols of those types are included. The run snapshots enabled rows in OrderSeq/Id order, and progress uses that same count. The table still shows total configured and enabled counts separately. Disabled rows and their history are retained; enabled flags are not changed. Confirmation stops local price sync and live studies before calculation. Other applications writing the same prices/studies should be paused during maintenance.

Calculation begins from the first source bar for a new regeneration and commits results in batches. The table shows each ColType's active StudyCol, committed bars, percentage and status. **Cancel operation** retains completed batches; closing during a run cancels and waits before closing. Committed batches contain binary outputs and OHLCV/checkpoints in StudyHistory and dbo.StudyRegeneration progress in one transaction. Prices and StudyCol definitions are retained. No checkpoint is restored when deliberately starting a fresh regeneration after a completed run.

The optional **Full** checkbox beside **Regenerate selected collections** always starts from the first bar. For each selected StudyCol, the first batch transaction deletes its existing StudyHistory and regeneration progress, then bulk-inserts the replacement results directly into StudyHistory. Subsequent batches also insert directly; binary studies and checkpoint payload/metadata are sent together without SQL temporary tables or output UPDATE/INSERT matching. Other collections, prices and definitions are retained. The last 100 study bars still receive source validation, using a locked ordered read without temporary tables. Logs report `Full history delete`, `Build direct buffers`, and `StudyHistory direct bulk insert` separately for performance comparison. Cancellation retains committed batches; **uncheck Full** to resume them through normal regeneration. Leaving Full checked deliberately deletes and restarts again. Until the first replacement batch commits, the old collection history remains intact; afterwards only regenerated batches are available.

### L2 base studies and overrides

StudyHistory now has nullable `StudiesOverride varbinary(max)`, using the same FIGS v1 format as Studies. For the L2 collection only, the host captures Studies immediately before the final `Study_L2` executes and puts its declared `IStudyKeyContract.WrittenStudyKeys` values into StudiesOverride. This preserves original base inputs even when Study_L2 overwrites a shared key. Plugins continue seeing the complete effective dictionary. Other collection types retain the single-payload behavior. Replacing an override replaces the entire payload, so obsolete strategy-only keys do not survive from a prior override. Full and normal regeneration and live updates all write both layers atomically.

Tools → Regenerate Studies → **L2 overrides (full last 10)** replays only Study_L2 from stored base values for bars before the last 10. The final 10 study bars (all bars for shorter histories) calculate the complete collection and publish OHLCV, Studies and StudiesOverride together in one transaction. Recent corrections or missing/new tail rows no longer require Full regeneration. Earlier base rows still need complete layered data matching current prices and configuration. The boundary is based on the study interval, including aggregate collections. Only enabled StudyCols run; this mode remains mutually exclusive with Full.

The full collection needs its runtime state before the tail. `dbo.StudyTailCheckpoint` retains a full native checkpoint at that boundary independently of override checkpoint cleanup. Normal regeneration captures this boundary state without changing the configured output batch size. Override runs restore it (or a compatible older full checkpoint), warm any gap, and transfer the newly replayed Study_L2 state and merged history into the full collection before calculating the tail. If no compatible full checkpoint exists, runtime state is rebuilt automatically from source prices; this can be expensive on the first run or after a DLL/core change, but earlier stored base rows are not rewritten. Checkpoint-disabled/unsupported plugins require this warm-up on every run. Successful tail publication includes a normal full checkpoint for subsequent live recovery. Deleting a StudyCol cascades to its cached tail state.

The initial base fingerprint covers only the earlier stored-input region, so corrections within the final 10 bars do not invalidate override-prefix recovery. Per-batch source/base checks remain transactional. Final validation reads at most 100 study bars: up to 90 unchanged base rows plus the freshly published tail. There is no final full-history payload reread. Changes to earlier base rows after their batch commits remain intentionally outside the final validation scope. The UI shows Preparing tail, Refreshing tail, Validating and Finalizing as appropriate; 100% and Completed appear after the final checks and completion persistence. Changes to earlier prices or base study algorithms/parameters still require full calculation. Deploy the updated app and shared libraries together; compatible existing L2 plugins need no changes. The core build change invalidates older native checkpoints once.

Readers must decode Studies, decode StudiesOverride when non-null, and overlay matching keys (including null values). `FIGCommon.Utilities.StudyValueCodec.Merge` implements this, and MainRepo/StudyHistoryRS return merged values to existing JSON API consumers. Old rows with null overrides remain valid combined results. FIGCharts currently reads CSV/FIGDATA files rather than SQL; any new SQL/export reader must merge the two columns before presenting values. Reading Studies alone no longer returns L2 strategy outputs for layered rows.

Interrupted/failed/cancelled runs resume from the newest compatible committed checkpoint. Definitions, DLL identity and input-prefix hashes are validated; changed inputs can require an earlier checkpoint or a fresh replay. A DLL without native checkpoint support (or disabled checkpointing) rebuilds its calculation state by replaying the committed prefix while retaining its committed database batches. Manual regeneration checks source prices only for the final 100 study bars of the starting snapshot (or all bars when fewer than 100 exist). Historical batches skip price staging and SQL price comparison; a batch crossing the boundary validates only the tail. Aggregate study bars validate all contributing raw source bars. Manual regeneration does not perform a final full-history price reread. Live updates, including large batched replays, retain full per-batch validation and their final full-source check. Changes in a validated range reject the affected batch. Historical prices must remain unchanged during manual regeneration; earlier corrections made while it runs are intentionally not detected. Stored output timestamps outside source coverage are reported rather than silently deleted. Source history is still loaded/read for validation; batching bounds result buffers and SQL writes, not all input memory.

Database settings now include **Study SQL timeout (seconds)** (`StudySqlTimeoutSeconds`, default 360) and **Study batch size (records)** (`StudyBatchSize`, default 1,000). These are local JSON settings with the normal Save/Cancel prompt. SQL timeout controls study command and bulk-copy waits, not CPU calculation duration. Increasing timeout can help large SQL operations, but batching avoids one enormous publication transaction. Large histories processed by Start Studies also use this batch path and durable progress. Restart workers after saving these limits.

## Stock search null-field handling

IBKR matching-symbol responses can omit Exchange, LocalSymbol, name and other optional strings. Stock filtering uses null-safe comparisons; stock rows without a routing exchange use SMART while preserving PrimaryExchange and the provider ID. Stock resolution passes the exact conId and primary listing exchange and sends no futures expiry. Stock historical requests also omit contract month. These paths are tested with a simulated MSFT/NASDAQ response containing null fields. Live lookup still requires a connected TWS/Gateway.

Type changes refresh exchange suggestions and clear known values from the other group. Custom identifiers remain editable. STK always disables/clears expiry; returning to FUT re-enables expiry with futures choices.

Processing timings are logged separately per committed regeneration batch and live replay: Calculation, Binary encoding, Checkpoint capture (native DLL), and Checkpoint serialization (JSON). These are monotonic wall times and include allocations/GC pauses inside the measured operation. SQL timings remain separate. Source-window validation materializes the locked price range once with a fresh range-query plan before comparing both directions; it still rejects corrections, additions and deletions before publication.

Regeneration invokes the existing study DLL in chunks of at most 16 bars, ending early at checkpoint and database batch boundaries. Bars still calculate sequentially, with cancellation checked per bar. The binary encoder reuses its working buffer and caches the most recent sorted field names and their UTF-8 bytes; each published payload owns its bytes. FIGS v1 bytes, study DLLs, native checkpoint state and recovery rules remain unchanged. Live replay also uses the reusable encoder.

A read-only benchmark on November 1, 2026 used 15,000 configured L2 study bars with three alternating runs per implementation. Average calculation/encoding pipeline time fell from 3.42 s to 2.53 s (26% less time); binary encoding fell from 1.21 s to 0.37 s (70% less time), and managed allocations fell from 3,262 MiB to 2,159 MiB (34% less). Calculation alone changed little (2.19 s to 2.14 s). Binary outputs and native checkpoints matched exactly, including checkpoint resume. These measurements exclude SQL writes and do not predict the same percentage improvement for end-to-end regeneration. The regression executable's `--benchmark-study-pipeline CONFIG_JSON OUTPUT_JSON` command repeats this bounded, read-only comparison without publishing results or changing configuration.

Regeneration batch publication retries SQL deadlock error 1205 at most three times after the initial attempt, with increasing randomized delays. Each retry opens a fresh connection/transaction, rechecks the source window and republishes the same calculated outputs/checkpoint/progress atomically. Cancellation stops retry backoff; other SQL errors, timeouts and source-change failures are not retried by this policy. Each failed attempt retains its uncommitted write timing and emits a retry message. Source-window extraction uses MAXDOP 1 and serializable shared range locks (HOLDLOCK), avoiding parallel exchange workers and unnecessary update locks while keeping price-change protection. This is query-local; no server-wide settings are changed.

On November 1, 2026, system_health event-file graphs at 07:20–07:21 UTC confirmed a parallel self-deadlock: all process nodes belonged to session 64, with update page locks on FIGMarketLive.dbo.PriceData and an exchangeEvent. The query-local MAXDOP 1 / shared-range-lock change targets this observed cycle. Reading these diagnostics required temporarily granted server permissions; the application does not need sysadmin to run the fix.

Configuration → Database places Test database and schema / Configure SQL notifications and their result box directly below connection settings. The Performance group underneath contains maximum price catch-up, backup reconciliation interval, SQL timeout, study batch size and checkpoint interval.

Validation scope is explicit per operation: Tools regeneration selects RegenerationTail, whereas the live engine selects Full. The log records the policy and marks historical validation as skipped. Definition checks, input sanity checks, checkpoint-prefix recovery checks, transaction retries, output coverage checks and atomic progress/checkpoint writes remain enabled in both modes.

Study Collections is a single top-level configuration tab containing Collections (StudyCol editing and OrderSeq controls) and Collection Types (plugin discovery, load errors and plugin folder settings). Both inner-page navigation and outer-tab navigation retain draft-discard and local-configuration Save/Cancel guards. Exchange Schedule follows this combined tab.
